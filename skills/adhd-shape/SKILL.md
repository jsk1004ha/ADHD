# Shape an executable first scope

Read the current request and supplied examples/templates first. For native
handoff read [the shared contract](../adhd-native/references/skill-handoff.md).
The parent keeps the existing execution owner and authorization.

## Resolve the consequential blanks

1. Identify the problem, affected person and concrete situation. Check a situation
   where the problem does not occur to avoid an unnecessarily broad scope.
2. Separate user-confirmed requirements, observed facts, agent assumptions and
   unresolved questions. Existing files may answer questions without an interview.
3. Ask the most consequential remaining question. Do not collect a full feature
   wish list or calculate a made-up ambiguity score. A reversible detail can be
   chosen and recorded; a conflicting central goal needs the user's answer.
4. Compare a few meaningfully different approaches only when the choice matters.
   Define the first complete useful result without discarding must-haves.
5. State included work, excluded work and evidence of completion. Record a time
   or money appetite only if the user supplies it; it is not an effort estimate
   and does not create permission to spend.

Return a short task brief: problem/user/situation; confirmed requirements;
assumptions and gaps; first scope and exclusions; explicit constraints; acceptance
evidence; next action. Scale its size to the actual task.

## Finish and hand off

Stop when another owner can implement and verify the requested result, or when
essential unresolved information is explicitly identified. If the request is only
to clarify the idea, deliver the brief. If implementation is already requested,
pass it into the current owner's plan without asking for routine confirmation.
Substantive shaping can itself be a research/report run with a real brief;
creating that run does not authorize the eventual product implementation.

Example: “실험 기록 정리 도구 아이디어를 구체화해 줘.” Read available records;
clarify the desired retrieval problem, preserve source links and date uncertainty,
then provide the first scope and its checks. Do not start coding from this prompt.

## Method inputs

Adapt the affected/unaffected-context questions from [Problem Framing Canvas](https://github.com/deanpeters/Product-Manager-Skills/blob/1b5a524ebb95e9497fa3f25002d8b8ec528d4444/skills/problem-framing-canvas/SKILL.md)
and scope/appetite/risks/exclusions from [Shape Up](https://basecamp.com/shapeup/1.5-chapter-06).
These are design techniques, not evidence that a proposed user need is verified.
